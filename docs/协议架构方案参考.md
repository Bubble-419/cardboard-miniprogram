# 轮询房间游戏状态同步重构设计

## 1. 目标

适用于基于云函数 / HTTP 短请求实现的房间类游戏或多人互动应用。

重构目标：

* 服务端状态唯一且权威
* 多用户并发 Action 不覆盖状态
* 客户端状态可稳定增量同步
* 刷新、断线、重启后可快速恢复
* Action、轮询、重连使用统一的数据模型
* 避免客户端状态、服务端状态、多份临时状态互相覆盖导致混乱

核心模型：

```text
Action   客户端 -> 服务端，表达“我要做什么”
State    服务端维护的权威房间状态
Event    服务端 -> 客户端，表达“发生了什么”
Snapshot 某个 seq 时刻的完整房间状态
```

---

## 2. 核心原则

### 服务端维护唯一权威状态

客户端不能直接决定业务状态。

例如：

```text
客户端发送 PLAY_CARD
```

不代表客户端可以直接认为“牌已经打出”。

正确流程：

```text
Action
  ↓
服务端读取当前房间状态
  ↓
服务端验证 Action 是否仍然合法
  ↓
修改权威 State
  ↓
产生 Event
  ↓
客户端消费 Event 更新本地状态
```

服务端始终根据**收到 Action 时的真实当前状态**裁决是否合法。

不要求客户端提交 `expectedVersion` 等业务版本。

---

## 3. Action、State、Event 分工

### Action

表示用户意图，例如：

```text
READY
PLAY_CARD
LEAVE_ROOM
CHANGE_SETTING
SEND_CHAT
```

Action 建议至少携带：

```json
{
  "actionId": "唯一 ID",
  "roomId": "room_xxx",
  "knownSeq": 100,
  "type": "PLAY_CARD",
  "payload": {}
}
```

其中：

* `actionId`：处理请求重试和幂等
* `knownSeq`：表示客户端已经完整消费到哪个 Event

Action 本身不能作为最终状态依据。

---

### State

服务端保存完整、权威的房间状态：

```json
{
  "roomId": "room_xxx",
  "stateVersion": 42,
  "eventSeq": 108,
  "state": {
    "phase": "playing",
    "players": [],
    "turn": "...",
    "game": {}
  }
}
```

`stateVersion` 表示房间核心状态提交次数，主要用于调试、日志和状态检查。

`eventSeq` 表示当前 Event 流已经推进到哪里。

二者不要混为一个概念。

---

### Event

Event 描述已经被服务端确认发生的事实，例如：

```text
101 PLAYER_JOINED
102 GAME_STARTED
103 CARD_PLAYED
104 TURN_CHANGED
```

每个 Event 都具有严格递增的：

```text
seq
```

客户端只能按 seq 顺序消费 Event。

Event 是客户端维护本地房间状态的唯一业务输入。

---

## 4. Snapshot + Event

客户端房间状态采用：

```text
Snapshot + 后续 Event
```

维护。

例如客户端获取：

```json
{
  "seq": 583,
  "state": { ...完整状态... }
}
```

表示：

```text
当前本地状态 = State@583
```

此后客户端只需要消费：

```text
584
585
586
...
```

即可持续得到最新状态。

核心不变量：

```text
Snapshot(seq=N)
+
Events(seq>N)
=
最新客户端状态
```

Snapshot 不要求是服务器“这一毫秒的最新状态”，但必须保证：

```text
state 和 seq 属于同一个一致状态
```

不能出现：

```text
state 实际只包含到 583
却返回 seq=585
```

否则客户端会永久漏掉 584、585。

---

## 5. 四类协议

整个客户端协议尽量只保留四种概念。

### 5.1 当前房间查询

轻量接口：

```text
GET current-room
```

只回答：

```json
{
  "roomId": "room_xxx",
  "status": "playing"
}
```

或者：

```json
{
  "roomId": null
}
```

用途：

* 小程序启动
* 页面刷新
* App 重启
* 判断用户当前是否已经在某房间

它不返回完整房间数据。

---

### 5.2 Snapshot

```text
GET room snapshot
```

返回：

```json
{
  "roomId": "room_xxx",
  "seq": 583,
  "stateVersion": 91,
  "state": {}
}
```

以下情况直接使用 Snapshot：

* 首次进入房间
* 刷新页面
* App 重启
* 断线重连
* 中途重新进入房间
* 客户端状态丢失
* Event 缺失
* 未消费 Event 过多
* 客户端无法确认当前状态是否正确

设计原则：

> 不要设计大量复杂恢复逻辑。
> 只要客户端无法确信状态正确，就丢弃本地状态并重新 Snapshot。

---

### 5.3 Action

```text
POST room action
```

服务端：

```text
读取当前房间状态
↓
验证 Action
↓
执行状态迁移
↓
生成 Event
↓
提交
```

Action Response 同时承担一次同步：

```json
{
  "action": {
    "actionId": "xxx",
    "accepted": true
  },
  "events": [],
  "currentSeq": 108
}
```

其中 `events` 的语义不是：

```text
“这个 Action 自己产生的 Event”
```

而是：

```text
“客户端 knownSeq 之后尚未消费的连续 Event”
```

因此如果客户端：

```text
knownSeq = 100
```

期间别人产生：

```text
101
```

当前 Action 又产生：

```text
102
```

Response 可以直接返回：

```text
101
102
```

这样 Action 本身就完成了一次同步。

---

### 5.4 Sync

当客户端没有 Action 时，通过：

```text
GET sync?after=xxx
```

获取：

```json
{
  "events": [],
  "currentSeq": 108,
  "snapshotRequired": false
}
```

Sync 只是兜底同步。

概念上可以理解为：

```text
Action = 做事情 + 顺便同步
Sync   = 什么都不做，只同步
```

---

## 6. 轮询调度

不要让 Action 和轮询同时不断请求服务器。

推荐：

```text
任何 Action Response
↓
视为已经完成一次同步
↓
重新延迟下一次 Sync
```

例如：

```text
Action
Action
Action
      ↓
   空闲 1 秒
      ↓
     Sync
```

如果 1 秒内又产生 Action：

```text
取消原 Sync Timer
重新从最后一次服务器 Response 后开始计时
```

所以实际策略是：

```text
用户活跃时：
依靠 Action Response 同步

用户空闲时：
每约 1 秒 Sync
```

应以：

```text
最后一次成功获得服务器状态的时间
```

作为调度基准，而不是 Action 发起时间。

---

## 7. 客户端只相信 seq

多个 HTTP / 云函数请求可能并发执行，也可能乱序返回。

因此：

```text
请求顺序 != 服务端执行顺序
响应顺序 != Event 顺序
```

客户端绝不能依赖 Response 顺序。

只认：

```text
event.seq
```

假设：

```text
lastSeq = 100
```

客户端必须连续消费：

```text
101
102
103
```

如果收到：

```text
102
```

却没有：

```text
101
```

说明产生 seq gap。

此时不要猜测状态，直接：

```text
触发 Sync
```

如果仍无法补齐：

```text
重新 Snapshot
```

---

## 8. 云函数并发与房间状态

传统房间服务器通常是：

```text
同一个 Room
Action A
Action B
Action C
```

由单线程顺序执行，因此天然不会发生状态覆盖。

云函数不同：

```text
Function A
Function B
```

可能同时读取：

```text
room version = 10
```

分别计算后覆盖彼此的数据。

因此核心房间状态必须具有数据库级并发保护。

推荐使用：

```text
数据库 Transaction
```

逻辑：

```text
Transaction
  ↓
读取最新 Room State
  ↓
根据最新 State 验证 Action
  ↓
执行 Reducer
  ↓
更新 Room
  ↓
写入 Event
  ↓
记录 actionId
  ↓
Commit
```

如果事务发生写冲突：

```text
重新读取最新 State
重新执行 Action
```

不能复用基于旧状态算出来的结果。

---

## 9. Action Reducer

推荐把核心游戏逻辑写成接近纯函数：

```ts
reduce(
  state,
  action
): {
  newState,
  events
}
```

即：

```text
Old State + Action
       ↓
     Reducer
       ↓
New State + Events
```

传统房间服务器靠：

```text
单线程
```

保证串行。

云函数架构则靠：

```text
Transaction
```

保证提交一致性。

业务逻辑本身不应该因此发生巨大变化。

---

## 10. Action 幂等

每个 Action 必须有：

```text
actionId
```

因为可能发生：

```text
客户端请求
↓
服务器执行成功
↓
Response 丢失
↓
客户端重试
```

如果没有幂等保护，同一个 Action 可能执行两次。

因此服务器需要识别：

```text
roomId + actionId
```

已经处理过的 Action 直接返回之前的结果，不再次修改状态。

---

## 11. Event 与 State 要原子提交

不能出现：

```text
Room State 更新成功
Event 写入失败
```

也不能：

```text
Event 写入成功
Room State 更新失败
```

因此一个核心 Action 的：

```text
Room State
Event
actionId 幂等记录
```

应尽量在同一 Transaction 中提交。

这样保证：

```text
客户端看到的 Event
一定对应已经成功提交的服务端 State
```

---

## 12. 核心状态与非核心数据分离

不要所有东西都修改同一个 Room Document。

适合放入核心 Room State：

```text
玩家列表
准备状态
游戏阶段
当前回合
牌局数据
胜负结果
```

聊天这类天然 append-only 数据可以单独存：

```text
roomMessages
```

避免：

```text
有人发一句聊天
↓
导致出牌事务冲突
```

类似地，日志、埋点、Presence 等弱一致性数据也尽量独立。

---

## 13. JSON 局部更新

云数据库支持文档局部更新时，应避免每次都替换整个大 JSON。

例如只修改：

```text
game.turn
game.phase
players.xxx.status
eventSeq
```

但不要为了“局部更新”过度拆分文档。

拆分边界应该优先根据：

```text
一致性边界
并发冲突边界
访问模式
```

而不是单纯按照字段多少。

---

## 14. Event 数量过多时

Event 是增量同步机制，不是永久恢复机制。

如果客户端：

```text
knownSeq = 100
```

服务器：

```text
currentSeq = 5000
```

没必要发送 4900 个 Event。

服务端可以返回：

```json
{
  "snapshotRequired": true
}
```

客户端直接重新请求 Snapshot：

```text
State@5000
```

然后从：

```text
5001
```

继续消费。

---

## 15. 推荐的数据模型

```text
rooms
└── roomId
    ├── stateVersion
    ├── eventSeq
    └── state
```

```text
roomEvents
├── roomId
├── seq
├── type
└── payload
```

```text
roomActions
├── roomId
└── actionId
```

```text
roomMessages
├── roomId
├── sender
├── createdAt
└── content
```

其中 `roomEvents` 推荐建立：

```text
(roomId, seq)
```

索引。

---

## 16. 客户端完整生命周期

```text
App 启动
   ↓
获取当前房间
   ↓
是否存在 roomId？
   │
   ├─ 否 → 大厅
   │
   └─ 是
       ↓
   获取 Snapshot
       ↓
   得到 State@seq
       ↓
   Action / Sync
       ↓
   按 seq 消费 Event
       ↓
   持续维护客户端状态
```

异常情况：

```text
seq gap
状态无法确认
积压 Event 太多
断线时间过长
App 重启
```

统一：

```text
丢弃本地房间状态
↓
重新 Snapshot
↓
继续消费 Event
```

---

## 17. 最重要的几个不变量

整个系统必须始终守住：

```text
1. 服务端 State 是唯一业务真相
```

```text
2. Action 表达意图，由服务端根据当前 State 裁决
```

```text
3. Event 表示已经确认发生的事实
```

```text
4. 客户端只通过 Snapshot + Event 构造业务状态
```

```text
5. Event 必须具有严格递增 seq
```

```text
6. Snapshot 的 State 与 seq 必须一致
```

```text
7. 客户端只相信 seq，不相信 HTTP 请求或响应顺序
```

```text
8. 核心 Room State 的并发修改必须受 Transaction / CAS 保护
```

```text
9. State、Event、Action 幂等记录应尽量原子提交
```

```text
10. 状态不确定时不要复杂恢复，直接重新 Snapshot
```

---

## 总结

整套架构可以概括成：

```text
客户端发送 Action
        ↓
服务端事务处理
        ↓
更新权威 State
        ↓
生成有序 Event
        ↓
客户端通过 Event 更新本地状态
```

客户端首次进入或无法继续可靠增量同步时：

```text
Snapshot
   +
后续 Event
```

重新建立状态。

Action Response 同时承担增量同步，只有在没有 Action 的空闲阶段才执行短轮询 Sync。

最终形成：

```text
服务端：
Action → State → Event

客户端：
Snapshot → Event → Local State
```

重构时不要围绕“如何把现在各种状态同步逻辑修补正确”继续增加特殊分支，而应围绕以上几个不变量重新收敛协议和状态流。
